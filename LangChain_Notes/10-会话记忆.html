理解 LLM 的无状态特性，掌握会话记忆的核心机制——如何在多轮对话中维护上下文、应对 Token 窗口限制，以及三种主流的记忆管理策略。这是构建流畅对话体验的基石。

时长 08:33 1.10 会话记忆 多轮对话基础

1 为什么需要会话记忆？

要理解为什么需要"记忆"，首先需要理解大语言模型的一个核心特性：LLM 是无状态的（Stateless）。

😩
无状态（默认行为）
每次请求都是独立的，模型不知道之前发生过什么
用户: "我叫小明"
AI: "你好小明！"

用户: "我叫什么？"
AI: "我不知道你的名字..."
✗ 模型失忆了！
🤝
有状态（带记忆）
每次请求携带完整历史，模型能理解上下文
用户: "我叫小明"
AI: "你好小明！"

用户: "我叫什么？"
AI: "你叫小明呀！"
✓ 记住了！
⚠️
核心问题：没有"记忆" = AI 每次都失忆。用户说"我叫小明"，下一轮问"我叫什么名字"，AI 完全不知道你在说什么。这是因为 API 服务端不保存任何对话状态——每次调用都是一次全新的推理过程。

2 实现会话记忆的核心机制

解决方案非常直观：在 messages 列表中维护完整的对话历史。每次发起新请求时，把之前的所有消息一起发送给模型。

Python - 手动实现会话记忆 
import requests
import os

# === 核心思路：维护一个 messages 列表 ===
messages = [
    {"role": "system",     "content": "你是一个有用的助手，请记住用户的个人信息。"},
    {"role": "user",       "content": "你好！"},
    {"role": "assistant",  "content": "你好！有什么可以帮您的吗？"},
]

def chat(user_input: str) -> str:
    """发送消息并更新历史记录"""
    // 1. 追加用户的新消息
    messages.append({"role": "user", "content": user_input})

    // 2. 发送完整的 messages 列表给 API
    response = requests.post(
        "https://api.deepseek.com/v1/chat/completions",
        headers={"Authorization": f"Bearer {os.getenv('DEEPSEEK_API_KEY')}",
        json={"model": "deepseek-chat", "messages": messages},
    )
    data = response.json()

    // 3. 获取助手回复
    assistant_reply = data["choices"][0]["message"]["content"]

    // 4. 将回复也追加到历史中（关键！）
    messages.append({"role": "assistant", "content": assistant_reply})

    return assistant_reply


# ========== 对话演示 ==========
print(chat("我叫小明"))       // 你好小明！很高兴认识你。
print(chat("我今年 25 岁"))   // 好的，我记住了，你叫小明，今年 25 岁。
print(chat("我叫什么？"))     // 你叫小明。
print(chat("我几岁了？"))     // 你 25 岁了。
💡
关键要点：
• 客户端保存状态 —— API 服务端不保存任何东西，所有历史由调用方维护
• 每次请求带上全量历史 —— 不是只发最新一条消息
• .append() 双向追加 —— 用户消息和助手回复都要追加到列表中
• system 消息只出现一次 —— 放在 messages 列表最前面作为全局指令

3 上下文窗口限制带来的挑战

"把全部历史消息都发给模型"听起来简单，但实际使用中会遇到一个硬性约束：上下文窗口（Context Window）是有限的。

常见模型的上下文窗口大小

模型上下文长度适用场景
GPT-4o-mini128K tokens长文档分析、大量对话历史
GPT-4o128K tokens通用场景，平衡能力与上下文
Claude 3.5 Sonnet200K tokens超长文档、代码仓库级分析
DeepSeek-V364K tokens日常对话、中等长度任务
Qwen2.5-7B (本地)32K tokens轻量本地部署，短对话
Llama 3.1-8B128K tokens开源模型中的长上下文王者

Token 消耗可视化

随着对话轮次增加，Token 数量线性增长。下图展示了在不同上下文窗口下，对话增长的趋势：

第 5 轮对话（约 1500 tokens） ~1% of 128K
安全
第 30 轮对话（约 9000 tokens） ~7% of 128K
安全
第 80 轮对话（约 24000 tokens） ~19% of 128K
注意
第 200 轮对话（约 60000 tokens） ~47% of 128K
危险
⚠️
三大挑战：
• Token 成本增加 —— 每轮都要重发全部历史，费用随对话长度累积
• 延迟变高 —— Token 越多，模型推理时间越长
• 可能溢出 —— 超出上下文窗口上限时会报 context_length_exceeded 错误

4 三种记忆管理策略

针对上述挑战，业界总结出了三种主流的记忆管理策略，各有优劣：

01
全量保存 (Full Buffer)
保留从对话开始至今的所有消息，不做任何裁剪或压缩。实现最简单，但 Token 消耗最大。
最简单 Token 重
02
滑动窗口 (Sliding Window)
只保留最近 N 轮对话，更早的消息被丢弃。Token 消耗恒定，但会丢失早期信息。
平衡型 可控成本
03
摘要压缩 (Summary)
用 LLM 定期将旧对话总结为精简摘要，保留摘要 + 最近 N 轮详情。智能但复杂度高。
最智能 额外 API 调用
对比维度全量保存滑动窗口摘要压缩
实现难度★★ 极简★★★ 简单★★★★★ 较复杂
Token 消耗线性增长恒定缓慢增长
信息完整性100%丢失早期近似保留
额外开销无无需调 LLM 做摘要
适用场景短对话 / 大上下文模型客服机器人 / 长对话深度咨询 / 复杂任务
🎉
实际选型建议：
• 短对话 (< 20 轮)：直接用全量保存，无需过度设计
• 中等对话 (20 ~ 100 轮)：滑动窗口是最实用的选择，保留最近 10~20 轮即可满足大多数需求
• 超长对话 (> 100 轮) 或 重要信息不能丢：考虑摘要压缩策略

5 与 LangChain Memory 的关系

好消息是：LangChain 已经将上述三种策略封装为标准组件，你不需要手动管理 messages 列表。只需选择合适的 Memory 类，LangChain 会自动处理一切。

LangChain 组件对应策略说明
ConversationBufferMemory 全量保存 将所有对话存储在内存缓冲区中，适合短对话场景
ConversationBufferWindowMemory 滑动窗口 只保留最近 K 轮对话，通过 k=N 参数控制窗口大小
ConversationSummaryMemory 摘要压缩 当 Token 超过阈值时自动调用 LLM 生成摘要
ConversationTokenBufferMemory Token 控制 基于 Token 数量而非轮数来控制保留范围，更精确
FileChatMessageHistory 持久化层 将对话历史保存到文件，配合上述任一 Memory 使用
