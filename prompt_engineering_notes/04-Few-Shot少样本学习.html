深入 LangChain Output Parser 体系——从 JsonOutputParser 到 PydanticOutputParser， 掌握让 LLM 输出精确可解析结构化数据的完整技术栈

01

为什么需要 JSON 格式控制

在 LangChain 的 LLM 应用开发中，一个反复出现且令人头疼的问题是：模型输出的自由文本无法被下游程序可靠地消费。 当你用 ChatGPT 做对话时，自由文本完全没问题；但当你试图把 LLM 嵌入到一个自动化 Pipeline 中时， 自由文本的「不可预测性」就会成为整个系统的阿喀琉斯之踵。

自由文本在生产环境中的三大致命缺陷

  • 不可解析（Unparseable）：同一个 prompt，模型可能这次返回 Markdown 表格、 下次返回 YAML 格式、再下次干脆就是一段带 emoji 的纯文字。正则表达式永远追不上模型的创造力—— 你写的匹配规则今天能工作，明天可能就因为模型多输出了一个换行符而失效。 根据 LangChain 社区的统计报告，约 23% 的首次 LLM 调用会因为格式问题导致后处理失败。
  • 不稳定（Unstable）：即使你精心设计了 prompt 来约束输出格式， 不同 temperature 设置、不同模型版本（如 GPT-4o vs GPT-4o-mini）、甚至同一模型在不同时段调用， 输出的格式细节都会发生漂移。字段顺序变化、引号类型切换（单引号↔双引号）、 多余空行插入、末尾附带解释性文字……这些微小的变化足以让你的 json.loads() 抛出异常。
  • 不可集成（Unintegrable）：现代应用架构中，LLM 的输出需要流入数据库、 传递给前端组件、写入消息队列或作为 API 响应返回。这些下游系统全部要求结构化的数据对象， 而非自然语言段落。没有标准接口意味着每处 LLM 接入点都需要定制化的后处理管道—— 维护成本随接入点数量线性增长。

为什么选择 JSON 作为目标格式？

在众多数据序列化格式（XML、YAML、Protocol Buffers、MessagePack 等）中， JSON 凭借以下五个核心优势成为 LLM 结构化输出的事实标准：

📦 全语言原生支持
Python 的 json.loads()、JS 的 JSON.parse()、Java 的 Gson……
零依赖即可获得字典/对象，无需引入额外序列化库
🔧 类型安全桥梁
配合 Pydantic v2 / TypeScript / dataclass，实现从 LLM 字符串到强类型对象的自动转换，IDE 补全和静态检查全程生效
📋 嵌套表达能力
天然支持任意深度的 object 和 array 嵌套，完美映射复杂业务实体（公司→部门→员工→技能树）
⚙️ 生态工具链成熟
JSON Schema 标准化验证、OpenAPI/Swagger 文档自动生成、ORM 映射、数据库迁移一气呵成
📝 双向可读性
机器友好 + 人类可读——调试时直接看原始输出，协作时团队成员都能理解数据结构
本集核心命题
如何以最小的工程成本，让 LLM 稳定地输出符合预定 Schema 的 JSON？

答案是 LangChain 的 Output Parser 体系——一套将格式约束声明式地注入 Prompt、 并在输出端自动完成解析和校验的工具链。本集将从最基础的 JsonOutputParser 讲到功能完备的 PydanticOutputParser，覆盖原理、实战、Schema 设计和错误处理的全链路知识。
02

JsonOutputParser 原理与 format_instructions 机制

JsonOutputParser 是 LangChain 中最轻量的 JSON 解析方案，位于 langchain_core.output_parsers 包中。它的设计哲学是：最小化用户配置， 最大化开箱即用的体验。你不需要定义任何 Schema，不需要写 Pydantic 模型—— 只需要告诉模型「请给我 JSON」，剩下的交给 Parser 自动处理。

核心机制：format_instructions 是什么？

这是理解整个 Output Parser 体系的钥匙。JsonOutputParser （以及所有其他 Parser）的核心能力来源是一个方法：get_format_instructions()。 这个方法会生成一段精心设计的提示文本，告诉 LLM 应该以什么格式输出。

Python / format_instructions 机制演示 
from langchain_core.output_parsers import JsonOutputParser

# Step 1: 创建 Parser 实例（无参数，零配置）
parser = JsonOutputParser()

# Step 2: 获取格式指令 —— 这是核心！
instructions = parser.get_format_instructions()

print(instructions)
# ──────────────────────────────────────────────
# 输出结果（实际生成的完整文本）：
#
# The output should be formatted as a JSON instance that conforms to the
# JSON schema below.
#
# As an example, for the schema {"properties": {"foo": {"title": "Foo",
# "type": "string"}}, "required": ["foo"], "type": "object"}
# the object {"foo": "bar"} matches the schema.
#
# As an example, for the schema {"properties": {"foo": {"title": "Foo",
# "type": "string"}, "bar": {"title": "Bar", "type": "number"}},
# "required": ["foo", "bar"], "type": "object"}
# the object {"foo": "bar", "bar": 123} matches the schema.
#
# As an example, for the schema {"$ref": "#/$defs/MyArray",
# "$defs": {"MyArray": {"items": {"additionalProperties": {},
# "properties": {"name": {"title": "Name", "type": "string"}, ...
# ──────────────────────────────────────────────
format_instructions 的本质
format_instructions = 一段注入 Prompt 的元指令（Meta-instruction）。

它做了三件事：
▶ 声明期望格式：「输出应为符合以下 JSON Schema 的 JSON 实例」
▶ 提供 Few-Shot 示例：展示 Schema 与合法 JSON 的对应关系
▶ 嵌入完整 Schema 定义：包含 properties、required、type 等约束

这段文本会被拼接到你的 Prompt 中，相当于给 LLM 加了一道「格式紧箍咒」。

完整用法示例：从创建到调用

Python / JsonOutputParser 完整 Pipeline 
from langchain_core.output_parsers import JsonOutputParser
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

# ══════════════════════════════════
# Step 1: 创建 Parser
# ══════════════════════════════════
parser = JsonOutputParser()

# ══════════════════════════════════
# Step 2: 构建 Prompt Template
# 关键：用 {format_instructions} 占位符预留位置
# ══════════════════════════════════
prompt = ChatPromptTemplate.from_messages([
    ("system", """你是一位专业的数据分析助手。
请从用户的描述中提取关键信息，并以 JSON 格式返回。

{format_instructions}

请只输出 JSON，不要添加任何额外的解释文字。"""),
    ("human", "{user_input}")
])

# ══════════════════════════════════
# Step 3: 用 LCEL 构建执行链
# pipe 操作符 | 将各组件串联为 Pipeline
# ══════════════════════════════════
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
chain = prompt | llm | parser

# ══════════════════════════════════
# Step 4: 执行并获取结构化结果
# ══════════════════════════════════
result = chain.invoke({
    "format_instructions": parser.get_format_instructions(),
    "user_input": (
        "苹果公司2024年第三季度营收达到943亿美元，"
        "同比增长6%，iPhone业务占比约50%，"
        "大中华区收入同比下降13%。"
    )
})

# ✅ result 已经是 Python dict！可以直接用
print(f"类型: {type(result)}")       # <class 'dict'>
print(result['company'])          # 苹果公司
print(result.get('revenue'))      # 943亿美元
# 典型输出：
# {'company': '苹果公司', 'revenue': '943亿美元',
#  'growth': '+6%', 'region': '大中华区',
#  'change': '-13%', 'quarter': '2024Q3'}

JsonOutputParser 内部处理流程详解

当你在 Chain 末尾挂上 JsonOutputParser 时，它在幕后完成了以下步骤：

阶段 操作 说明
1. Pre-parse Markdown 剥离 检测并移除 ```json ... ``` 代码块包裹符（模型常犯的错误之一）
2. Parse json.loads() 将清洗后的字符串解析为 Python dict 对象
3. Post-process 自动修复 尝试修复常见问题：尾随逗号、单引号→双引号、未转义字符等
4. Return 类型转换 返回 dict 或 list[dict]，可直接用于后续逻辑
JsonOutputParser 的局限性
它不校验字段的类型和结构。

返回的是裸 dict——你期望的 rating 字段可能是数字也可能是字符串； 必填字段可能缺失；嵌套结构的深度不可控。

适用场景：快速原型、简单键值对提取、对格式精度要求不高的场景。
生产环境推荐：升级到 PydanticOutputParser（下一节详讲），获得完整的类型安全保障。
03

PydanticOutputParser 深度讲解：四步流水线

如果说 JsonOutputParser 是一把瑞士军刀，那 PydanticOutputParser 就是一台精密机床——它能做到的不只是「解析 JSON」，而是定义 → 约束 → 验证 → 类型化 的全链路自动化。它是 LangChain 中生产级结构化输出的标准方案。

Step 1：用 Pydantic BaseModel 定义数据 Schema

一切从 Pydantic 模型开始。每个字段通过 Field() 描述其含义、类型和约束条件。 这些 description 会自动出现在 format_instructions 中，成为指导 LLM 输出的微型提示词。

Python / Pydantic Schema 定义（含嵌套模型） 
from pydantic import BaseModel, Field
from typing import Optional, List
from enum import Enum

# ─── 枚举类型：限制模型输出范围 ───
class Sentiment(str, Enum):
    POSITIVE = "正面"
    NEGATIVE = "负面"
    NEUTRAL = "中性"
    MIXED = "混合"

class AspectItem(BaseModel):
    """评价维度条目（嵌套子模型）"""
    aspect: str = Field(
        description="评价维度名称（如：口感/服务/环境/性价比/包装）"
    )
    sentiment: Sentiment = Field(
        description="该维度的情感倾向"
    )
    detail: Optional[str] = Field(
        None,
        description="该维度的具体描述（如果原文有提及）"
    )
    keywords: List[str] = Field(
        default_factory=list,
        description="该维度相关的关键词（2~5个）",
        min_length=0,
        max_length=5
    )

class ProductReview(BaseModel):
    """产品评论的结构化提取模型（顶层 Schema）"""
    
    product_name: str = Field(
        description="评论涉及的产品名称"
    )
    
    overall_sentiment: Sentiment = Field(
        description="整体情感倾向"
    )
    
    rating_score: Optional[float] = Field(
        None,
        ge=0, le=5,
        description="评分分数（0-5分制，原文未提及时为 null）"
    )
    
    aspects: List[AspectItem] = Field(
        description="按维度拆解的评价列表（至少1个，至多8个）",
        min_length=1,
        max_length=8
    )
    
    summary: str = Field(
        description="一句话总结这条评论的核心观点（不超过100字）",
        max_length=100
    )
    
    purchase_intent: Optional[bool] = Field(
        None,
        description="是否表达了购买意愿（true/false/null 表示未明确表达）"
    )

# 你可以随时查看 Pydantic 自动生成的 JSON Schema：
print(ProductReview.model_json_schema())

Step 3：将格式指令注入 Prompt 模板

Python / Prompt 模板构建与指令注入 
from langchain_core.prompts import ChatPromptTemplate, HumanMessagePromptTemplate
from langchain_core.messages import SystemMessage

# 使用 ChatPromptTemplate 构建结构化 Prompt
# 关键点：{format_instructions} 占位符会在运行时被替换
prompt_template = ChatPromptTemplate.from_messages([
    SystemMessage(content="""你是一位专业的电商评论分析师。
你的任务是从用户的产品评论中提取结构化信息。

## 输出要求
{format_instructions}

## 分析规则
1. 仔细阅读全文，不要遗漏任何评价维度
2. 情感判断要基于上下文，不能只看单个形容词
3. 如果原文没有明确提到评分，rating_score 设为 null

    HumanMessagePromptTemplate.from_template("{review_text}")
])

# 填充模板变量
prompt_value = prompt_template.format_prompt(
    format_instructions=format_instructions,
    review_text="""买了这款蓝牙耳机用了两周，说说真实感受：

续航大概能撑6小时左右，比我之前那个强。
但是佩戴舒适度一般，戴久了耳朵有点疼。
客服响应很快，问的问题都耐心解答了。

)

Step 4：构建 LCEL Pipeline 并执行

Python / 完整 Pipeline 执行与结果消费 
from langchain_openai import ChatOpenAI
import json

# 初始化 LLM（temperature=0 保证输出稳定性）
llm = ChatOpenAI(model="gpt-4o", temperature=0)

# ═══ LCEL Pipeline：Prompt → LLM → Parser ═══
# | 操作符将三个组件串联成一个 Runnable 链
chain = prompt_template | llm | parser

# 执行调用
result: ProductReview = chain.invoke({
    "format_instructions": format_instructions,
    "review_text": "（同上文的耳机评论）"
})

# ════════════════════════════════════════
// ✅ result 是强类型的 ProductReview 对象！
// IDE 能提供完整的类型提示和自动补全
# ════════════════════════════════════════

print(f"产品名: {result.product_name}")
# 产品名: 蓝牙耳机

print(f"情感: {result.overall_sentiment.value}")
# 情感: 正面

print(f"评分: {result.rating_score}")
# 评分: 4.0

// 遍历嵌套的 aspects 数组
for aspect in result.aspects:
    print(f"  [{aspect.aspect}] {aspect.sentiment.value}: {aspect.detail}")
    # [音质] 正面: 比预期好不少，低音有质感
    # [续航] 正面: 能撑6小时左右
    # [佩戴舒适度] 负面: 戴久了耳朵有点疼
    # [客服] 正面: 响应很快，耐心解答
    # [性价比] 正面: 这个价位算不错

print(f"总结: {result.summary}")
# 总结: 音质和续航表现优秀，佩戴舒适度有待改进，
    # 性价比高适合学生群体

// 导出为标准 JSON 字符串（可直接存入数据库或发送 API）
json_output = result.model_dump_json()
print(json_output)
# {"product_name":"蓝牙耳机","overall_sentiment":"正面",...}
PydanticOutputParser 的三位一体能力
格式指令生成 + 自动解析 + 运行时校验，三者无缝衔接。

▶ 格式指令：从 Pydantic Model 自动生成详细的 JSON Schema 描述，注入 Prompt
▶ 自动解析：接收 LLM 文本输出，剥离 markdown 包裹，解析为 Python 对象
▶ 运行时校验：类型检查、范围验证、必填字段检查——不符合则抛出 ValidationError

你只需定义一次 Model，整条管线全自动运行。这就是「声明式编程」在 LLM 应用中的完美体现。
04

Schema 设计最佳实践与反模式

Schema 设计的质量直接决定了 LLM 输出的准确率和解析成功率。 一个设计良好的 Schema 可以让模型轻松遵循；而一个糟糕的 Schema 则会导致频繁的格式错误和字段缺失。 本节汇总了来自 LangChain 官方文档、社区最佳实践和生产环境的经验法则。

黄金法则一：Description 即提示词

每个 Field(description=...) 中的描述文本不仅是文档——它们会被原封不动地嵌入 format_instructions，最终出现在发给 LLM 的 Prompt 中。这意味着：

Python / Description 写法对比 
from pydantic import BaseModel, Field

# ❌ 反模式：描述太模糊
class BadSchema(BaseModel):
    name: str = Field(description="名字")
    value: float = Field(description="数值")

# ✅ 最佳实践：描述具体、带示例、限定范围
class GoodSchema(BaseModel):
    company_full_name: str = Field(
        description="公司的法定全称（如'贵州茅台酒股份有限公司'，
                      不是简称也不是股票名）"
    )
    revenue_amount: Optional[float] = Field(
        None,
        description="营业收入金额（单位：亿元人民币，仅填数字，
                      如 943.0 表示 943 亿元）"
    )
    reporting_period: str = Field(
        description="财报周期，格式为 YYYYQn（如 2024Q3）或 YYYY年度（如 2024年度）"
    )

黄金法则二：Optional 的艺术

  • 必填字段（无 Optional）：仅用于任务绝对必需的核心信息。 如提取任务中的实体名称、分类任务的类别标签。必填字段过多会导致模型被迫编造值。
  • 可选字段（Optional[T] = None）：用于可能不存在的补充信息。 如股票代码、详细金额、时间戳等。当原文没提及时，模型应输出 null 而非编造。
  • 经验公式：在一个 Schema 中，必填字段数量建议控制在 3~5 个以内， 其余全部标记为 Optional。这样既保证核心信息的完整性，又给模型足够的灵活性。

黄金法则三：枚举约束优于自由文本

Python / Enum 约束 vs 自由文本对比 
from enum import Enum

# ✅ 用 Enum 严格约束输出范围
class DocumentType(str, Enum):
    ANNUAL_REPORT = "年报"
    QUARTERLY_REPORT = "季报"
    NEWS_ARTICLE = "新闻"
    RESEARCH_REPORT = "研报"
    COMPANY_ANNOUNCEMENT = "公告"
    OTHER = "其他"

class RiskLevel(str, Enum):
    LOW = "低风险"
    MEDIUM = "中风险"
    HIGH = "高风险"
    CRITICAL = "严重风险"

class ExtractionResult(BaseModel):
    doc_type: DocumentType = Field(description="文档类型分类")
    risk_level: RiskLevel = Field(description="内容风险评估等级")
    
    # Enum 生成的 format_instructions 会明确列出所有可选值：
    # "enum": ["年报", "季报", "新闻", "研报", "公告", "其他"]
    # 模型只能从中选择，彻底杜绝了 "新闻报道稿"、"财务报表" 等变体

黄金法则四：嵌套层次控制在 3 层以内

嵌套层级 解析成功率 推荐场景 注意事项
1 层（扁平） ★★★★★ ~98% 简单键值对提取 最稳定的首选方案
2 层（一层嵌套） ★★★★☆ ~92% 主实体 + 子项列表 大多数场景的最佳平衡点
3 层（两层嵌套） ★★★☆☆ ~82% 复杂业务实体 可接受，但需充分测试
4+ 层（深层嵌套） ★★☆☆☆ <70% 不推荐 考虑拆分为多次提取

常见反模式（Anti-patterns）速查

❌ 反模式 1
Schema 中全是必填字段，模型被迫为不存在的信息编造值
❌ 反模式 2
Field description 只写了字段名的中文翻译，没有说明取值规则和格式
❌ 反模式 3
嵌套超过 4 层，单次提取试图获取过于复杂的结构
❌ 反模式 4
用 str 类型接收本应是数值的字段，丢失类型安全
05

输出解析失败的处理策略

即使有了完美的 Schema 和精心设计的 Prompt，LLM 仍然可能输出不符合要求的内容—— 这是大语言模型的固有特性，无法完全消除。生产级代码必须具备多层容错防线， 在解析失败时优雅降级而非直接崩溃。

策略总览：四层防御体系

Python / 生产级鲁棒解析器（完整实现） 
import json
import re
import logging
from pydantic import ValidationError
from typing import TypeVar, Generic
from langchain_core.output_parsers import PydanticOutputParser

logger = logging.getLogger(__name__)
T = TypeVar('T', bound=BaseModel)

class RobustParser(Generic[T]):
    """
    鲁棒的 Pydantic 输出解析器
    
    实现四层容错策略：
    Layer 1: 直接 json.loads() + model_validate()
    Layer 2: 剥离 Markdown 代码块包裹符后重试
    Layer 3: 正则表达式提取 JSON 片段后重试  
    Layer 4: 全部失败时触发 Fallback 或抛出明确异常
    """
    
    def __init__(self, parser: PydanticOutputParser):
        self.parser = parser
        self.model_cls = parser.pydantic_object
    
    def parse(self, raw_output: str, strict: bool = False) -> T:
        """
        解析 LLM 原始输出为目标 Pydantic 模型
        
        Args:
            raw_output: LLM 返回的原始文本
            strict: True 时跳过所有容错策略，直接抛出异常
            
        Returns:
            T: 目标 Pydantic 模型的实例
            
        Raises:
            ValueError: 所有策略均失败时抛出
        """
        if strict:
            return self._layer1_direct_parse(raw_output)
        
        # 尝试四层策略
        strategies = [
            (self._layer1_direct_parse, "直接解析"),
            (self._layer2_strip_markdown, "MD 包裹剥离"),
            (self._layer3_regex_extract, "正则 JSON 提取"),
        ]
        
        for strategy_fn, name in strategies:
            try:
                result = strategy_fn(raw_output)
                logger.info(f"JSON 解析成功 (策略: {name})")
                return result
            except (json.JSONDecodeError, ValidationError, ValueError) as e:
                logger.debug(f"策略 [{name}] 失败: {e}")
                continue
        
        # Layer 4: 全部失败
        error_msg = (
            f"所有解析策略均失败。\n"
            f"原始输出前 300 字符: {raw_output[:300]}"
        )
        logger.error(error_msg)
        raise ValueError(error_msg)
    
    def _layer1_direct_parse(self, raw: str) -> T:
        """Layer 1: 直接解析（理想路径）"""
        data = json.loads(raw.strip())
        return self.model_cls.model_validate(data)
    
    def _layer2_strip_markdown(self, raw: str) -> T:
        """
        Layer 2: 剥离 Markdown 代码块
        
        LLM 经常在 JSON 外面套上 ```json ... ``` 包裹符，
        这里统一移除这些噪音后再重试解析。
        """
        cleaned = raw.strip()
        
        # 移除 ```json 开头和 ``` 结尾
        patterns = [
            r'^```(?:json)?\s*',     # 开头的 ```json 或 ```
            r'\s*```\s*$',           # 结尾的 ```
            r'^.*?```\s*',           # 开头到第一个 ``` 的所有内容
            r'^.*?(?=\{)',           # 第一个 { 之前的内容
        ]
        
        for pattern in patterns:
            cleaned = re.sub(pattern, '', cleaned, flags=re.DOTALL)
        
        if not cleaned.strip():
            raise ValueError("清洗后内容为空")
        
        data = json.loads(cleaned)
        return self.model_cls.model_validate(data)
    
    def _layer3_regex_extract(self, raw: str) -> T:
        """
        Layer 3: 正则提取 JSON 片段
        
        当模型在 JSON 前后附带了额外解释文字时，
        用正则从中提取出合法的 JSON 部分。
        """
        # 匹配 JSON 对象 {...}
        obj_match = re.search(r'\{[\s\S]*\}', raw)
        if obj_match:
            try:
                data = json.loads(obj_match.group())
                return self.model_cls.model_validate(data)
            except (json.JSONDecodeError, ValidationError):
                pass
        
        # 匹配 JSON数组 [...]
        arr_match = re.search(r'\[[\s\S]*\]', raw)
        if arr_match:
            try:
                data = json.loads(arr_match.group())
                return self.model_cls.model_validate(data)
            except (json.JSONDecodeError, ValidationError):
                pass
        
        raise ValueError("正则未找到有效 JSON")


# ══════════════════════════════════════════════
# 使用方式：替换原来的 parser 为 RobustParser
# ══════════════════════════════════════════════
def safe_parse_chain(llm_output: str, parser: PydanticOutputParser):
    """安全的解析包装函数，带重试和日志"""
    robust = RobustParser(parser)
    try:
        return robust.parse(llm_output)
    except ValueError as e:
        # 生产环境中这里可以触发重试逻辑或 fallback 流程
        logger.warning(f"解析失败，启用 fallback: {e}"
        return fallback_handler(llm_output)

def fallback_handler(raw: str):
    """Fallback：返回一个部分填充的结果或默认值"""
    # 实际项目中可以根据需求自定义 fallback 行为
    return {"_raw": raw, "_parse_failed": True}

Retry with Fix：LangChain 内置的重试机制

除了自行编写容错逻辑，LangChain 还提供了内置的 OutputFixingParser—— 当初始解析失败时，它会自动将错误信息反馈给 LLM，请求修正输出。

Python / OutputFixingParser 自动修复 
from langchain.output_parsers import OutputFixingParser
from langchain_openai import ChatOpenAI

# 创建一个"修复者" LLM（可以用更便宜的模型来降低成本）
fixer_llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

// 用 OutputFixingParser 包装原始 Parser
// 当 parse 失败时，它会自动：
// 1. 捕获 ValidationError 的详细信息
// 2. 构建一条 fix prompt（包含错误信息和原始输出）
// 3. 发送给 fixer_llm 请求修正
// 4. 用修正后的输出重新尝试解析
fixing_parser = OutputFixingParser.from_llm(
    llm=fixer_llm,
    parser=parser,  # 你的 PydanticOutputParser
    max_retries=2   # 最多重试 2 次
)

// 替换 chain 中的 parser
chain = prompt_template | llm | fixing_parser

// 现在 chain 会自动处理大部分格式错误！
// 成功率通常可以从 ~85% 提升到 ~96%+
注意事项
OutputFixingParser 会增加延迟和 token 消耗。每次重试都意味着一次额外的 LLM 调用。

▶ 推荐配置：fixer_llm 用轻量模型（gpt-4o-mini），max_retries 设为 1~2
▶ 成本考量：在高并发场景下，优先用 RobustParser 的本地容错策略（零额外 API 调用）
▶ 组合策略：先走 RobustParser 四层策略 → 全部失败后再触发 OutputFixingParser 重试

LangChain 的 Output Parser 体系不止前面介绍的两种。在实际项目中， 根据场景选择合适的 Parser 是优化性能和控制成本的关键一步。 下面是完整的对比分析和选型决策树。

RetryOutputParser 任意文本 取决于内层 Parser 继承自内层 继承自内层 继承自内层 需要完整重新调用的场景
