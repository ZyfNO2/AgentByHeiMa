01

Prompt 的本质与定义

提示词（Prompt）是大语言模型（Large Language Model, LLM）的输入接口——它是用户以自然语言形式向模型传达意图、提供上下文、约束输出行为的全部文本内容。 从技术本质上讲，Prompt 是 LLM 推理引擎的「编程语言」： 你不需要写 Python 或 C++，但你需要用自然语言精确地「编程」模型的思维过程。

从 GPT-3 到现在：Prompt Engineering 的演进脉络

2020.06 — GPT-3 发布
OpenAI 发布 1750 亿参数的 GPT-3，首次展现出Few-Shot Learning（少样本学习）能力。 研究者发现：通过在输入中提供少量示例（in-context examples），模型无需微调即可完成新任务——Prompt Engineering 的雏形由此诞生。 Brown et al. 在论文中系统性地描述了 "prompting" 这一范式。
2021-2022 — 探索期
学术界涌现大量 prompting 研究：Chain-of-Thought (Wei et al., 2022) 提出「思维链」推理； Zero-Shot CoT (Kojima et al., 2022) 发现仅加一句 "Let's think step by step" 就能显著提升推理能力； Self-Consistency (Wang et al., 2022) 通过多次采样投票提升准确率。Prompt 开始被视为一门可研究的科学。
2022.11 — ChatGPT 爆发
ChatGPT 面向公众开放，Prompt Engineering 从学术研究走向大众实践。 数亿用户开始用自然语言与 AI 对话，「如何写好 prompt」成为全民关注的话题。 GitHub 上 prompt 相关仓库星数激增，社区开始沉淀最佳实践。
2023-2024 — 工程化成熟期
LangChain、LlamaIndex 等 Prompt 编排框架出现；企业级应用中 Prompt 变成需要版本管理、A/B 测试、监控追踪的一等公民； System Prompt 与 User Prompt 分离、Prompt Template 引擎、Prompt Cache 等工程概念逐渐标准化。 Microsoft、Google、Anthropic 各自发布官方 Prompt Engineering Guide。
2025+ — Agent 时代
随着 LLM 能力边界不断拓展，Prompt Engineering 正在向 Agent Design 演进—— 不再只是单轮对话优化，而是涉及多步推理规划、工具调用编排、记忆管理、自我反思等更复杂的系统级 Prompt 设计。

什么是「提示词工程」（Prompt Engineering）？

提示词工程是指设计和优化输入给大语言模型的文本指令， 以引导模型产生期望输出的系统性方法与实践。它不是简单的「提问技巧」，而是一门融合了：

语言学
理解自然语言的歧义性、指代消解、语用含义对模型行为的影响
认知心理学
借鉴人类沟通中的框架效应、锚定效应、启发式原则来设计指令
软件工程
将 Prompt 视为代码进行版本控制、测试、迭代和团队协作管理
机器学习
理解 Transformer 注意力机制、tokenization、temperature 等底层原理
核心认知：Prompt = LLM 的源代码
把 Prompt 想象成你写给一个极其博学但完全不了解你背景的超强实习生的工作指令。 这个实习生能理解几乎所有领域的知识，但他不知道你的具体需求、不知道你的受众是谁、不知道你对输出格式的要求。 Prompt Engineering 就是学会如何给这个实习生写一份清晰、完整、无歧义的工作说明书。 写得越好，他的产出就越符合预期——这和写代码让计算机执行逻辑在本质上是同一件事。
02

提示词设计的核心原则

经过学术界和工业界的大量实践验证，以下三大核心原则构成了高质量 Prompt 设计的基石。 这些原则并非孤立存在，而是相互补充、协同作用的——一个好的 Prompt 通常会同时满足多条原则。

原则一：清晰且具体（Be Specific & Explicit）

这是最基础也最重要的原则。模糊的指令迫使模型「猜测」你的意图， 而猜测的结果往往不尽如人意。清晰的指令应当包含： 任务类型、目标受众、输出格式、长度约束、风格要求等可量化、可验证的具体参数。

Bad vs Good — 清晰度对比：文本摘要任务 
# ❌ Bad — 模型不知道：摘要给谁看？多长？什么格式？保留什么信息？
prompt_bad = "帮我总结一下这篇文章"

# ✅ Good — 六个维度全面明确
prompt_good = """
【任务】请为以下科技新闻撰写一段执行摘要。

【目标读者】非技术背景的公司高管，他们关注商业影响而非技术细节。

【要求】
1. 字数控制在 150-200 字之间
2. 必须包含以下要素：核心事件（1句话）、影响范围（谁受影响）、
   商业意义（为什么重要）、关键数据（如有）
3. 使用专业但不晦涩的语言，避免行话缩写
4. 采用「倒金字塔」结构——最重要信息放在最前面

【输出格式】纯文本段落，不要使用列表或 Markdown 格式

【待处理文本】
{article_text}
"""

原则二：提供充分上下文（Provide Context）

LLM 是一个无状态的无记忆系统——每次调用之间没有持久化的上下文。 你认为显而易见的信息，对模型来说可能完全未知。 上下文就像是模型的「临时工作记忆」，你注入的信息越丰富、结构化程度越高， 模型的推理质量就越好。有效的上下文应覆盖以下四个维度：

👤 角色身份
"你是一名有 10 年经验的资深后端架构师，精通分布式系统设计"
🎯 使用场景
"这段代码将被集成到一个日活千万的电商交易链路中"
📋 背景信息
"我们使用 Spring Boot 3.x + MySQL 8.0 + Redis Cluster 架构"
⚠️ 约束条件
"不能引入新的中间件依赖，改动范围限制在 Service 层以内"
Bad vs Good — 上下文丰富度对比：代码审查任务 
# ❌ Bad — 零上下文，模型只能做泛泛的语法检查
prompt_bad = "审查这段代码有没有问题：\n{code_snippet}"

# ✅ Good — 完整上下文让模型做出有针对性的深度审查
prompt_good = """
【角色】你是一位专注于高并发系统的资深代码审查专家，
       有 15 年 Java 后端开发经验，曾主导过双11大促的核心链路优化。

【项目背景】
这是一个电商订单服务的库存扣减模块，当前面临以下问题：
- QPS 峰值达到 50000，现有实现存在超卖风险
- 数据库连接池经常耗尽，导致服务熔断
- 团队中有 3 名初级开发者会参与维护此代码

【审查重点】
1. 并发安全性：是否存在竞态条件或数据不一致风险？
2. 性能瓶颈：是否有不必要的数据库查询或锁竞争？
3. 可维护性：代码是否足够清晰，便于初级开发者理解和修改？
4. 异常处理：边界情况是否都考虑到了？

【约束】
- 不要建议重构整个模块（业务方不允许大改）
- 只指出 P0 和 P1 级别的问题
- 每个问题给出具体的修复代码示例

【待审查代码】
```java
{code_snippet}
```
"""

原则三：分解复杂任务（Decompose Complex Tasks）

当面对复杂的多步骤任务时，将其拆解为多个独立的子任务是提升输出质量的关键策略。 这背后的原理是：LLM 的注意力机制（Attention Mechanism）在处理长文本时会出现信息稀释现象—— 当 Prompt 超过一定长度（通常 500+ token 的指令部分），模型对各子指令的关注度会下降， 导致遗漏要求或执行不完整。

Bad vs Good — 任务分解对比：技术文档生成 
# ❌ Bad — 一个 Prompt 塞入 5 个子任务，模型容易遗漏
prompt_bad = """
根据这个 API 项目，生成完整的技术文档，包括：
1. API 接口列表和参数说明
2. 数据库 ER 图描述
3. 部署指南
4. 故障排查手册
5. 性能调优建议
"""

# ✅ Good — 分步骤执行，每步聚焦单一目标
# Step 1: 先提取 API 信息
prompt_step1 = """
分析以下代码，提取所有 API 端点信息。
输出 JSON 数组，每个元素包含：method, path, parameters, return_type。
只做提取，不做其他分析。
"""

# Step 2: 基于 Step 1 输出生成接口文档
prompt_step2 = """
基于以下 API 端点信息，生成 OpenAPI 3.0 规格的接口文档。
每个接口需包含：描述、请求参数表、响应示例、错误码说明。
"""

# Step 3: 单独处理部署相关内容
prompt_step3 = """
基于项目配置文件（Dockerfile, docker-compose.yml, README），
生成部署指南。包含环境变量清单、启动命令、健康检查端点。
"""
新手常犯的 5 个错误
  • 「万能 Prompt」陷阱：试图用一个超长 Prompt 覆盖所有需求，结果每个需求都被敷衍处理
  • 矛盾指令冲突：同时要求「详细深入」和「简洁精炼」，模型陷入两难
  • 假设模型知道背景：不说清楚自己的行业、场景、术语含义，指望模型自动猜对
  • 忽略输出格式约束：不指定 JSON schema / 表格列名 / 字段含义，然后抱怨解析报错
  • 一次性定型不复盘：写完 Prompt 就不再测试不同输入，错过了通过迭代优化的机会

四要素详解

要素 英文 核心问题 作用 典型写法
指令 Instruction 做什么？ 定义任务的行动动词和目标 "翻译"、"总结"、"分类"、"分析"、"重写"
上下文 Context 为什么？谁在看？ 提供背景信息、角色设定、领域知识 "你是一名..."/"这是用于..."/"目标读者是..."
输入数据 Input Data 处理什么？ 需要模型操作的具体内容 待翻译文本 / 待分析代码 / 用户提问内容
输出指示 Output Indicator 怎么输出？ 约束格式、风格、长度、结构 "JSON格式"/"不超过200字"/"表格呈现"/"正式语气"

四要素的设计要点与权衡

指令 (Instruction)
用强动词开头 · 避免被动语态 · 一个 Prompt 一个核心动作 · 可叠加子指令但要分层
上下文 (Context)
按 角色→场景→约束 顺序组织 · 只放相关信息避免噪声 · 复杂上下文可用独立段落
输入数据 (Input)
用分隔符明确界定边界 · 超长输入先做预处理 · 敏感数据注意脱敏
输出指示 (Output)
指定格式必附示例 · 给出字段语义说明 · 设定明确的验收标准
四要素使用的关键经验
  • 不必每次四要素齐全：简单翻译任务只需「指令 + 输入 + 输出格式」，复杂的分析任务才需要全部四个
  • 推荐排列顺序：Instruction → Context → Input Data → Output Indicator，这与人类的阅读习惯一致
  • 用视觉分隔符增强结构感知：=== 、### 、--- 、【】等标记帮助模型（和你自己）快速定位各区域
  • Output Indicator 是最被低估的要素：花 80% 的时间构思指令，却只用 5 秒想输出要求——这是最常见的低效模式
  • Context 和 Input 的边界要清晰：Context 是「元信息」（关于任务的信息），Input 是「原始数据」（要被处理的内容），混在一起会让模型困惑
04

主流 Prompt 设计框架

除了通用的四要素模型，业界还衍生出了多种特定场景下的 Prompt 设计框架（Framework）。 这些框架本质上是四要素的不同组合方式和命名体系，各自适用于不同的任务类型和使用习惯。 选择合适的框架可以让 Prompt 设计更加系统化和可复现。

框架总览

🎯 RTF 框架
Role — Task — Format
最经典的三段式框架。先设定角色身份（Role），再明确任务（Task）， 最后规定输出格式（Format）。简单易记，适合绝大多数日常场景。 是新手入门的首选框架。
Role Task Format
⭐ CO-STAR 框架
Context — Objective — Style — Tone — Audience — Response
由新加坡 Google Developer Group 提出，在 RTF 基础上增加了 Style（风格）、Tone（语气）、 Audience（受众）三个维度，特别适合营销文案、 内容创作等需要精细控制输出风格的场景。
Context Objective Style Tone Audience Response
💥 BROKE 框架
Background — Role — Objectives — Key Results — Evolve
受 OKR 管理方法论启发的框架，强调可衡量的结果（Key Results） 和持续迭代（Evolve）。 特别适合复杂的项目规划、方案设计类任务， 让 Prompt 本身具有「项目管理」的思维结构。
Background Role Objectives Key Results Evolve
📋 RISEN 框架
Role — Input — Steps — Examples — Nuance
强调步骤分解（Steps）和示例驱动（Examples）的框架， 适合需要精确控制推理过程的技术类任务（代码生成、数据分析、数学推导）。 Nuance（细微差别）要素提醒注意边界条件和特殊情况。
Role Input Steps Examples Nuance
🔄 CREATE 框架
Character — Request — Example — Adjust — Type — Evaluation
一个迭代式框架，内置了 Adjust（调整）和 Evaluation（评估）环节。不只是「一次生成」， 而是「生成 → 评估 → 调整 → 再生成」的循环流程， 适合对输出质量要求极高的创意写作和专业内容生产。
Character Request Example Adjust Type Evaluation
🧩 APE 框架
Action — Purpose — Expectation
最精简的三要素框架，来自 Andrej Karpathy 等人的实践总结。 Action（做什么动作）、Purpose（为什么做）、 Expectation（期望什么结果）。 适合快速原型设计和轻量级任务，是「最小可行 Prompt」的最佳模板。

通用场景 / 新手入门 RTF 学习成本最低，适用面最广
重要提醒：框架是工具，不是教条
这些框架的价值在于提供结构化的思考 checklist，而不是让你机械地填空。 高手往往是内化了框架之后跳出框架——你可能不会显式地标注「Role:」「Task:」这样的标签， 但你的 Prompt 结构天然地涵盖了这些要素。学习的正确路径是： 先用框架规范自己 → 熟练后形成直觉 → 最终根据场景自由组合。

📋 Prompt 自检 Checklist（写完必查）

生产级 Prompt 质量检查清单
  • [ ]  单一职责：这个 Prompt 是否只聚焦于一个核心任务？（避免一 Prompt 多任务）
  • [ ]  指令清晰：任务动词是否明确？（翻译/总结/分类/生成/分析……而不是"看一下"）
  • [ ]  上下文充分：是否说明了谁在使用、什么场景、什么约束？（角色/背景/限制条件）
  • [ ]  输出格式确定：是否指定了 JSON/Table/List/纯文本？是否给了字段说明或示例？
  • [ ]  长度约束：是否有字数/Token 数/条目数量的上限或下限？
  • [ ]  结构分明：四要素是否用分隔符清晰划分？（模型和你自己都能快速定位）
  • [ ]  无矛盾指令：是否存在互相冲突的要求？（如"详细"vs"简洁"、"正式"vs"活泼"）
  • [ ]  鲁棒性验证：是否用至少 3 种不同的输入测试过？（正常/边界/异常 case）
